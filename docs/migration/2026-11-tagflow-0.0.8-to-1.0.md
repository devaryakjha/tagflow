# Migrating from Tagflow 0.0.8 to 1.0

This guide takes an app from the `0.0.x` HTML renderer (latest `0.0.8`, kept
on the `stable` branch) to the `1.0` line. It covers what changes, what keeps
working, and how to rewrite the custom converters most apps have.

The earlier [alpha migration guide](2026-06-11-tagflow-v1-alpha-migration.md)
explains the runtime design in more depth. This guide is the short path.

## What changed

In `0.0.x`, `Tagflow(html: ...)` parsed HTML into `TagflowNode`s and turned
each one into a widget with an `ElementConverter` picked by CSS-like
selectors.

In `1.0`, content is a typed `TagflowDocument` of `TagflowDocumentNode`s. HTML
is one input: `TagflowHtmlAdapter` turns it into a document, and Markdown and
native JSON have their own adapters. A `TagflowComponentRegistry` renders each
node by its `TagflowNodeKind` (paragraph, heading, list, table and so on).

You customize rendering by node kind, not by HTML selector.

## Upgrade steps

1. Pin exact versions while the line is in beta:

   ```yaml
   dependencies:
     tagflow: 1.0.0-beta.2
     tagflow_table: 1.0.0-beta.2 # if you render tables
   ```

2. Run `dart fix --apply`. It rewrites the mechanical changes for you:
   `Tagflow(html: ...)` to `Tagflow.html(...)`, `TagflowOptions` to
   `TagflowViewOptions` (when no `renderBoundary` is passed), `options:` to
   `viewOptions:`, `ErrorWidgetBuilder` to `TagflowErrorWidgetBuilder`, and
   it removes the no-op `loadingBuilder:` and `enableImageCache:` arguments.

3. Move each custom converter to a registry builder (below). Until you do,
   `Tagflow.html(converters: [...])` still runs them through the legacy
   pipeline, so you can migrate one converter at a time.

4. Update golden tests. Spacing, colours and text flow now follow the
   ambient `Theme` through `TagflowRenderTheme`.

## Basic rendering

Before (`0.0.8`):

```dart
Tagflow(
  html: html,
  options: TagflowOptions(
    linkTapCallback: (url, attributes) => launchUrl(Uri.parse(url)),
    selectable: const TagflowSelectableOptions(enabled: true),
  ),
)
```

After (`1.0`):

```dart
Tagflow.html(
  html: html,
  viewOptions: TagflowViewOptions(
    linkTapCallback: (url, attributes) => launchUrl(Uri.parse(url)),
    selectable: const TagflowSelectableOptions(enabled: true),
  ),
)
```

`Tagflow.markdown(markdown: ...)` and `Tagflow.document(document)` render the
other inputs the same way.

## Theming

`TagflowTheme` still works and now feeds the runtime renderer. For new code,
use `TagflowRenderTheme`, which has typed fields for each built-in component
and falls back to the ambient Material `Theme`:

```dart
Tagflow.html(
  html: html,
  renderTheme: const TagflowRenderTheme(
    paragraphSpacing: 12,
    linkStyle: TextStyle(color: Colors.teal),
  ),
)
```

Use `TagflowRenderThemeScope` to theme a whole subtree.

## Custom converters

### Restyling a tag

Before, a converter for one tag:

```dart
class QuoteConverter extends ElementConverter<TagflowElement> {
  const QuoteConverter();

  @override
  Set<String> get supportedTags => {'blockquote'};

  @override
  Widget convert(
    TagflowElement element,
    BuildContext context,
    TagflowConverter converter,
  ) {
    return Card(
      child: Padding(
        padding: const EdgeInsets.all(12),
        child: Column(
          children: converter.convertChildren(element.children, context),
        ),
      ),
    );
  }
}

Tagflow(html: html, converters: const [QuoteConverter()]);
```

After, a registry override for the node kind:

```dart
final registry = TagflowComponentRegistry(
  overrides: {
    TagflowNodeKind.blockquote: (context, node) => Card(
      child: Padding(
        padding: const EdgeInsets.all(12),
        child: context.renderBlockContent(node),
      ),
    ),
  },
);

Tagflow.html(html: html, registry: registry);
```

`context.renderBlockContent(node)` renders the children like the built-ins
do, flowing inline runs as one paragraph. `context.render(child)` renders a
single child. Both keep registry precedence (your overrides, then extensions
such as `tagflow_table`, then the built-ins), so nested content still uses
your overrides.

Create the registry once, for example in a top-level `final` or a state
field, rather than in `build`.

### Selectors and classes

Selectors such as `div.note` or `ul > li` have no registry equivalent. Read
the HTML provenance on the node instead:

```dart
final registry = TagflowComponentRegistry(
  overrides: {
    TagflowNodeKind.container: (context, node) {
      final classes = node.htmlAttributes['class']?.split(' ') ?? const [];
      if (!classes.contains('note')) return context.renderBlockContent(node);
      return ColoredBox(
        color: Colors.amber.shade50,
        child: context.renderBlockContent(node),
      );
    },
  },
);
```

An override for `container` also receives inline containers such as `span`,
which then render as their own widget inside the paragraph. Check
`node.presentation.display == TagflowDisplay.inline` if you only mean block
containers.

### Custom elements

Before, a converter for an app-specific tag such as `<my-card data-id="7">`.

After, map the element to a `custom` node once, after adapting, and register
a builder for that type. Unknown HTML elements arrive as `unsupported` nodes
that keep their children and attributes:

```dart
TagflowDocumentNode mapCards(TagflowDocumentNode node) {
  final children = node.children.map(mapCards).toList();
  if (node.kind == TagflowNodeKind.unsupported && node.htmlTag == 'my-card') {
    return TagflowDocumentNode.custom(
      id: node.id,
      type: 'card',
      metadata: TagflowMetadata(node.htmlAttributes),
      children: children,
    );
  }
  return node.copyWith(children: children);
}

final document = const TagflowHtmlAdapter().parse(html);
final mapped = document.copyWith(
  children: document.children.map(mapCards).toList(),
);

final registry = TagflowComponentRegistry(
  customComponents: {
    'card': (context, node) => Card(
      child: ListTile(
        title: Text('Card ${node.metadata['data-id']}'),
        subtitle: context.renderBlockContent(node),
      ),
    ),
  },
);

Tagflow.document(mapped, registry: registry);
```

If you were rendering a tag that the content policy blocks (`script`,
`iframe`, form controls), it is now removed during adaptation. Loosen the
policy on the adapter only for content you trust.

### Tables

Before:

```dart
Tagflow(html: html, converters: [TagflowTableConverter()]);
```

After:

```dart
final registry = TagflowComponentRegistry(
  extensions: [tagflowTableComponents()],
);

Tagflow.html(html: html, registry: registry);
```

Without `tagflow_table`, the core renders tables as a plain grid that does
not draw row or column spans.

## What keeps working, and for how long

- `Tagflow(html: ...)`, `TagflowOptions`, `converters:` and
  `package:tagflow/legacy.dart` (parser, `ElementConverter`, `TagflowNode`
  models) are deprecated but keep working through every `1.x` release. They
  are removed in `2.0`.
- `TagflowTableConverter` and `TagflowTableCellConverter` follow the same
  schedule.
- `loadingBuilder` and `enableImageCache` did nothing on the runtime path and
  are removed before `1.0.0`. `dart fix` deletes them.

## Behavior differences to check

- HTML whitespace collapses as the CSS specification says, and inline runs
  wrap as one paragraph instead of one widget per run.
- The content policy drops `script`, `style`, `iframe` and form controls,
  allows only `http`, `https` and `mailto` URLs, and rejects `data:` images.
- Documents deeper than 128 levels or larger than 50000 nodes are cut off
  (`TagflowContentPolicy.maxDepth` and `maxNodes`).
- Colours follow the ambient theme, including dark mode.
